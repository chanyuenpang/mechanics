# ADR：发布后本机运行环境必须切换到 registry 正式包

## 背景

npm 发布成功不代表本机全局 `mech` 或 DSH web profile 已改用发行包：开发阶段的源码 link/file 可能保留，即使版本数字一致，实际运行的仍是仓库内容。插件还需新 DSH 进程加载，离线工具预检与登录后的对话图卡可见性也不是同一种验收。

## 决策

每次发布对应 Mechanics CLI 或 DSH 插件后，发布流程必须先确认 registry 的精确已发布版本，再用 npm 与 `dsh plugin` 官方安装命令把本机正在使用的对应包替换成该正式版本。按实际解析路径、profile 安装声明和插件依赖核查来源；不允许 `link:`、`file:`、`workspace:` 或仓库源码路径作为本机正式包验收。项目 `mech sync` 是另一个独立步骤，不代替运行包安装。

承载当前对话的 DSH 实例在重新加载插件前，须按重启流程取得本次明确同意；未获确认时只能完成安装并报告待重启。重启后分别验收服务/路由和已登录浏览器内的实际图卡；不能以包版本、预检或图页 HTTP 200 代替后者。具体命令由 `docs/更新与升级.md` 和 `packages/dsh-adapter/docs/安装与回滚.md` 维护，当前事实归 CLI 与 DSH 两篇 Truth owner。

## 备选方案

- 继续保留源码 link，只看版本数字：无法证明发布包内容及其依赖被实际使用，故拒绝。
- 手工修改 profile 或启动另一个 DSH server：绕过官方安装和当前会话的加载边界，不能证明现有 GUI 已切换，故拒绝。
- 安装后立即重启：可能中断当前用户会话；重启授权与安装完成分开处理。

## 后果

发布状态、本机安装状态与当前进程加载状态需分别报告；任一环节失败时不得笼统称“本地已更新”。本次切换的历史验收在正式包 0.9.0/插件 0.1.4 与服务层达成，登录后的图卡视觉呈现没有由该次验收证明；这些版本和进程结果不作为未来版本的恒定承诺。
