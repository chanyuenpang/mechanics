# ADR：DSH 图卡按工具结算独立挂载

## 背景

Code Mode 的 `mechanics_graph` 以 PTC 子派发完成，子事件缺少 turn；若直接按子事件所属轮次挂载，聊天流没有可靠的位置，图工具成功也不代表对话可见。图卡还可能被工作过程折叠，与最终答复的位置要求混淆。

## 决策

当前客户端以带轮次位置的 `run_code` 或原生 `mechanics_graph` 根 `tool/call` 建立调用上下文，以 `rootCallId` 关联成功子派发，在工具结算序列之后发布独立 `mechanics-widget` 聊天节点；同根多次成功成图各保留一个 widget，图页面根据会话 `cwd` 定位项目。节点可见性不等于其折叠容器可见性：只在可挂载成功图卡且所属轮次可折叠、当前关闭时，通过公开 `turnProcess` 控制器在 effect 中展开轮次，不依赖外部折叠插件。这个决定解决图卡在折叠过程区的可见性，不承诺图卡紧贴或位于 final 回复之后；当前实现不接入 `conversation.chat.turnTail`。当前行为的唯一 Truth owner 是 `../features/dsh-adapter-and-chat-widget.md`。

## 备选方案

- 直接按子派发的 turn 放置：子派发不带 turn，会丢失正确轮次位置，不能作为可靠锚点。
- 使用 final 后的收尾席位：当时未采用，涉及轮次折叠和序列边界；未来若必须在 final 后展示，应独立设计并验证该方案，不能把现有独立节点当作已满足要求。
- 依赖未知节点触发外部折叠插件的 fail-open：旧客户端注释有此意图，但安装 profile 是否有该插件与当前 DSH 折叠行为无保证，不能作为当前验收合同。

## 后果

对话可见、图页面可用、折叠展开与最终位置必须独立验收。两个已初始化项目的真实图调用和用户可见确认支持基础可见性；0.1.3 的折叠修复另经真实 DSH 页面验收，相关回归覆盖展开门禁及同根多图互不串改高度。展开仅作用于可挂载图卡所属的折叠轮次，不应在渲染期间更新宿主状态或为失败调用打开轮次。图卡不在 final 回复位置仍是后续缺陷，不得归入本决策已解决范围。客户端事件、聊天节点槽位或 DSH 折叠策略变化后，须重新核验原生及 PTC 路径、失败路径、折叠和 final 位置。
