# 游戏机制建模工作流

只在用户明确要求创建、修改或删除机制模型时使用。唯一写入入口是受约束的 `game-graph agent mechanic-folder create|delete`、`game-graph agent mechanic create|update|delete`、`game-graph agent view delete`、`game-graph agent concept create|update|delete`、`game-graph agent rule add|update|delete`，以及经项目清单约束的 `game-graph agent recipe-migration preview|execute`；禁止直接编辑 `.game-graph/`、调用原始 HTTP mutation、修改生成机制文档，或通过网页和脚本绕开约束。

本技能的维护范围仅为当前项目注册副本。工具包中的同名源文件应在本副本经真实任务验证后再同步更新。

## Agent 编辑会话：普通写入的必经协议

机制图编辑不是一组彼此无关的 mutation。Agent 对既有机制图进行普通概念、规则、机制元数据或排版写入时，必须连接已经运行的本地服务，并以一次明确的打开和关闭包围这一轮编辑：

1. 读取 `game-graph agent scopes --project <绝对项目目录> --connect http://127.0.0.1:<端口>`，取得该项目的 `projectGeneration`、顶层 `revision` 与逐资源 `resourceRevisions`。`--project` 只定位服务后台项目上下文，**绝不切换网页当前标签**；不要为模型写入重启服务。
2. 先执行 `game-graph agent mechanic open --project <绝对项目目录> --mechanic <ID> --project-generation <当前代次> --connect <origin>` 解析目标。返回 `existing` 时，才执行 `agent session open`；返回 `create-required` 时，只能用当前 `workspaceRevision` 创建空机制图，创建后重读 `scopes`，再显式 `session open`。机制目标 open 不产生 session，也不能写入。不同机制会话彼此独立；只有同一 Agent 已知自己的未关闭会话时，才在下一次 open 加 `--previous-session <旧session>`，服务才会异步关闭**指定旧会话**，绝不猜测或关闭其他 Agent 的图。
3. 新建 `mechanic-folder` 与空机制图的 `mechanic create` 是容器准备操作：携带 `--project <绝对项目目录>`、`--project-generation <当前代次>`、`--connect <origin>` 和当前 `--workspace-revision`，不需要 `--session`；每次创建后先重读 `scopes`。对已存在机制的其他 mutation（概念、规则、更新、删除与视图）必须携带 `--session <session>`，以及原本要求的 `--revision` 或 `--workspace-revision`。规则或机制操作的 `--mechanic` 必须等于会话打开的机制；跨图写入会以 `AGENT_EDIT_SCOPE_MISMATCH` 拒绝。
4. 编辑完成只触发、不等待：`game-graph agent session close --project <绝对项目目录> --mechanic <ID> --session <session> --project-generation <当前代次> --connect <origin>`。它立即返回 `accepted: true`、`asynchronous: true` 和 `jobId`；后台队列随后以最新资源版本执行整图 `arrange`、发布并回读。Agent 不必轮询后再开始下一张图。
5. 仅当后续步骤确实依赖关闭结果、或用户报告布局失败时，才调用 `game-graph agent session status --project <绝对项目目录> --session <session> --project-generation <当前代次> --connect <origin>`。状态为 `closed` 才表示 `result.arranged: true`；`failed` 必须暴露 `failure`，不得把它改写为成功。

`projectSessionToken` 仅属于网页多标签路由，不是权限凭据，也不应传给 Agent CLI。`session open|close|status` 只能通过已运行本地服务调用，不能用 `--project` 离线替代。CLI 仍保留离线 mutation 作为兼容入口；它不具备异步会话、自动关闭或写入准入保障，**本技能禁止在普通 Agent 建模中使用它**。固定清单的 `recipe-migration`、schema `migrate` 与 `repair` 是独立原子/修复操作，不属于单图编辑会话，按各自流程执行。

会话本身不持有 `.game-graph.lock`；锁仍只覆盖每次实际读改写提交。服务退出会取消内存会话，重新连接后必须重新 `open`，不能假定旧 session 仍可写入。

## 常用操作矩阵

| 场景 | 唯一正确入口 | 版本与收尾 |
| --- | --- | --- |
| 单图概念、规则、范围或机制元数据编辑 | `session open` → 受约束 mutation → `session close` | 写入前取逐资源版本；close 异步整理与回读。 |
| 新机制文件夹或空图 | `mechanic-folder create` / `mechanic create` | 每次容器创建后回读顶层 revision；创建完再 open 目标图。 |
| 多机制规则归属迁移 | `agent recipe-migration preview` → `execute` | 只使用 preview 返回的工作区 revision；事务已负责必要容器、组合视图、排版与回读。 |
| 已知 schema 升级或悬空节点修复 | `game-graph migrate --from <版本> --to <版本> --project <目录>`，确认 preview 后加 `--revision <预览版本> --execute` | 不是规则建模；只执行 CLI 列出的受支持版本对。 |
| 已删除限定词/边遗留投影坐标 | `game-graph repair projection-positions --project <目录>`，确认 preview 后加 `--revision <预览版本> --execute` | 只删除不再被任一规则引用的投影坐标；不得手改 canonical。 |
| `AGENT_EXPORT_FAILED` 且 `canonicalCommitted:true` | 停止依赖 mutation，记录 revision 后只读回查 | canonical 已写入；绝不自动重试或声称回滚。 |
| `SAVE_UNCERTAIN`、版本冲突、会话 `failed` | 停止受影响链路，读取真实状态与错误 | 只按已确认的修复入口恢复；不得用网页/脚本绕过。 |

## 多机制规则归属迁移

当一张旧机制图的规则需要拆分到多张机制图，并以组合视图替代旧总览时，禁止串行调用 `rule delete/add`：全局同向端点唯一约束会制造重复或缺边窗口。必须使用项目内 `docs/` 的固定迁移清单，先执行 `recipe-migration preview` 并记录返回的工作区 `revision`，再以该 revision 执行 `recipe-migration execute`。该单事务只迁移 canonical 中已有的完整边对象，保留规则文字、限定词、继承和 ID；成功时同时创建必要的非空机制、删除旧 owner、建立同 ID 组合视图、自动排版和回读。布局、版本、校验或提交任一步失败时不应写入半成品。

`recipe-migration recover` 是仅在 `workspace.json` 已因已知提交器故障丢失时才允许使用的灾难恢复入口；它只从固定清单和仍存在的 definitions 重建最终机制归属与总览，旧布局记忆不可被伪称已恢复。

## 每轮必须留下的工作产物

短任务可在回复中呈现，复杂任务可写入任务报告；它们是分析记录，不是第二份机制真相。

1. **范围与证据表**：玩法问题、适用版本、抽象粒度、机制/视图 ID、revision；每个候选概念须分别记录**事实依据**（当前实现、已声明规则、运行时结论或未知）与**设计依据**（作者已确认的后续机制目标或无）。两类依据不得互相替代。
2. **规则母表与逐规则决策表**：每条规则的性质、触发、行动者、目标及同一对象绑定、读取量、写入量、顺序、例外/优先级、证据；以及其候选边、限定词、反例与“保留 / 修改 / 删除 / 未决”结论。
3. **写入与回读清单**：每个授权 mutation 的前后字段、resourceRevision 串联顺序、实际返回值与回读结果。

## 核心运转规则：规则优先，图只作投影校验

优化对象始终是**规则说明能力**，不是节点数、连线长度或画布形状。执行顺序固定为：

1. 从已有资料、作者确认或运行时证据整理规则卡；
2. 为每张规则卡确定不可省略的参与对象、变化和例外；
3. 仅为承担独立规则职责的对象建立概念和边；
4. 最后检查图的单链、孤点、纯分类父节点等形状，且只能把它们作为“要求回查规则卡”的信号，不能直接作为删除理由。

每张规则卡必须包含：`性质（当前事实 / 已确认设计 / 未决）`、`触发`、`参与对象及同一对象绑定`、`状态变化或结果`、`例外/条件`、`证据来源`。规则卡是审查母表；机制图中的每条边和每个节点都必须能回指至少一张规则卡。没有规则卡的图形结构不构成玩法证据。

概念的保留理由只能是下列之一：

- 它在一张或多张当前事实规则卡中承担独立输入、输出、状态、事件或判定职责；
- 它是作者明确确认的设计锚点，并有一张已确认设计规则卡说明计划接入的方向。

单链中间节点仅是审查信号：收集它关联的全部规则卡后，若它只是在同一规则卡中把 `A → B` 的结算拆开，且可将触发、对象绑定、数值、例外完整写回 `A → B` 的规则文字，才可压缩。若其他规则实际消费的是其中的事件或来源，应为该事件/来源另立规则卡和候选概念；不得因此保留语义不符的中间数值。不能完整保留语义时，保留或标为未决。

## 八阶段流程

### 1. 定义问题与范围

1. 写清本轮要解释或改变的玩法问题、抽象粒度、目标机制/视图，以及模式：`审查` 或 `写入`。先选择具体玩法问题和适用版本，例如“有效伤害如何结算并影响战斗结果”，不得把“减少节点或边”当作问题本身。先声明本轮的规则来源，不得把当前画布当作规则来源；分析请求绝不推断为写入授权。
2. 先运行 `game-graph agent guide --format text` 与 `game-graph --help`，以当前工具合同为准；确认 `agent session open|close|status`、`mechanic arrange`、迁移与修复命令均由当前 CLI 提供。技能中的参数说明不能覆盖实际 CLI。
3. 运行 `game-graph agent scopes`，或对已确认运行的服务使用 `--connect`，记录 workspace、顶层 `revision` 与 `resourceRevisions`。容器创建使用顶层 `revision`；概念与规则写入使用逐资源版本。视图审查须列出纳入的机制；不能把视图当作全工作区。
4. 若范围、权限、稳定 ID 或工作区版本不明确，停在审查并报告未知，不进入写入。

### 1.5 先分解机制层级与颗粒度，再建立任何概念

当请求包含“完整建模”“某游戏/系统的机制建模”或目标范围跨越多个玩法问题时，必须先产出并获得可执行的**机制容器计划**。不得直接把收集到的全部规则写进第一个机制图。

1. 先从玩家可感知的玩法问题分解，而不是从名词清单分解。通常按“游戏循环 / 子系统 / 可独立说明的局部机制”三层审视：
   - **游戏循环层**只保留跨子系统的入口、阶段转换、终局或资源闭环；它不是全部规则的汇总图。
   - **子系统层**说明一个可独立阅读的玩法域，例如战斗、地图推进、经济、成长或构筑。
   - **局部机制层**说明一个在子系统内可单独提出并回答的问题，例如一次行动结算、伤害结算、抽牌与牌区流转、商店购买。单张卡牌、道具或单位只有在它拥有独立、可复用的结算规则时才成为局部机制图；否则其规则归属到对应子系统或结算机制图。
2. 为每个候选机制图写一条**读者问题**和边界：它解释什么、从哪些概念或事件开始、产生什么结果、明确不解释什么。若两张图不能各自回答不同问题，合并；若一张图需要读者同时理解多个弱关联流程，拆分。节点数、边数或文件数不是拆分依据。
3. 先列出文件夹树和图清单。每张图至少记录 `id`、名称、父文件夹、粒度层级、读者问题、scope、规则归属、跨图输入/输出和证据状态。文件夹只负责导航与归类，不自动成为一张机制图。
4. 对每条规则卡指定**唯一的机制图归属**。概念可以跨图复用，但同一有向基础端点对在全工作区只能有一条规则；跨图依赖通过共享概念、规则卡中的输入/输出和图 scope 表达，绝不复制同一条边到多个图。
5. 先创建完整的文件夹树和空白机制图，再开始概念和规则 mutation。每创建一个容器后回读 `scopes` 更新顶层 revision；容器计划与实际创建结果不一致时，先修正计划，不得边写规则边临时把未归类的规则塞入已有图。
6. 最低限度的层级可以只有一个文件夹和一张图；只有当范围确实只回答一个玩法问题时才允许如此。对“完整游戏建模”默认要求至少检查并明确记录：核心循环、主要子系统及其局部结算机制是否需要分别成图；不能以“先做一张总图”作为未分解的默认值。

### 2. 建立证据表

1. 先用 `claw search --query` 找历史约定、Truth、ADR 与设计资料；再用 GitNexus 查当前代码/调用链。索引不足时才用 `rg` 精确回源；涉及实际行为时再检查运行时或测试证据。
2. 每项证据标明性质：已实现、作者声明、历史约定或未知。作者已确认的设计目标可以成为“设计锚点”的保留依据，不能伪装成当前运行时事实，也不能据此补造玩法连线；证据冲突时保留冲突并缩小结论。
3. 对计划保留但当前未形成独立机制的概念，记录具体预期接入的机制方向或作者确认语句；“以后可能会用”不是设计依据。无事实依据且无明确设计依据的候选必须标记为待压缩，不能默认保留。
4. 证据不足不自动删除、保留或补造规则；将该项标为“未决”，说明最小待补证据。

### 2.5 用场景校验规则母表

在投影前，为每个含顺序、阈值、例外或对象绑定的规则选择最小反例场景。至少核对：完全被防护吸收、部分结算、边界值、同一批次的互斥结果，以及来源或目标不同的情形。场景不能替代运行时测试，但能暴露“图上两条边看似可合并、规则实际不能合并”的错误；冲突或遗漏先回到规则母表，不用画布补猜。

### 3. 先写可读规则句

对每个候选规则先写完整规则卡：**性质、在何条件下、谁对谁造成什么变化、何种例外，以及依据是什么**。明确行动者、目标、持有者或对应对象。

- 跨端点的“自己的”“同一目标”“对应施加者”，以及量词、时序、数值门槛，先写入规则文字；当前模型没有变量、比较或绑定字段，不能宣称结构已经验证这些关联。
- 规则文字不参与结构推理或自动求值。边只声明抽象影响，不证明时序、概率、数值或运行时成立。
- **数值、事件与来源归属分开审查**：某个数值被结算不代表“该数值”值得成为概念；后续规则可能实际消费的是受击事件、施加者或卡牌来源。数值中间量可压缩，但被其他规则独立读取的事件应另写规则卡、另判断是否需要事件概念，不能借用数值节点代替它。

### 4. 映射概念、端点与边

1. 用 `search/graph/node` 核对稳定 ID、既有边与引用；不得按显示名称猜 ID。
2. 先执行**概念准入检查**，再创建或保留概念：
   - **事实概念**必须是当前玩法中的独立规则边界。仅对“源 → 中间节点 → 目标”中的单入单出**中间节点**，要求其在完整审查范围内参与该链之外的其他关系；否则它是压缩候选。链条端点不能只按度数判冗余。
   - **设计锚点**可暂不满足事实概念条件，但必须有作者明确确认的未来机制用途；在概念说明和证据表中写明“设计预留”及预期接入方向。它不增加当前玩法事实，不能以预留名义制造额外规则。
   - 两者皆非时，删除节点并把规则句压回直接端点；数值、命中、防护、同一对象绑定与例外写在该边的规则文字。
   - 端点已有且语义明确的属性才可作为限定词；其余条件保留在规则文字。
3. `specializes`（`is-a`）仅表达真实的“子类 → 上位概念”。父概念必须参与至少一条实际玩法规则并帮助理解共同玩法；只有分类边的父概念是冗余概念。
4. 当前关系仅为 `influence` 与 `specializes`。`influence` 必须指定 `--sign positive|negative|random`；`specializes` 不带 sign 或限定词。全工作区同一有向基础端点对只允许一条边。

### 5. 逐边反证与覆盖检查

1. 以规则卡为母表做**规则—概念覆盖检查**：列出每个节点承担的规则卡职责、每条边对应的规则卡、每张规则卡是否有足够投影。再对完整 scope（需要时为纳入全部相关机制的 view）列出每个节点的入边、出边和所在机制；入度、出度均为 1 的中间节点只进入压缩复审，不能仅因度数删除。不要只凭当前画面位置、单图可见性或概念描述判断复用。
2. 以 `graph` 返回的**全部声明边**为母表，逐条记录：机制、边 ID、源/目标、规则句、限定词、条件/绑定、反例、证据和结论。审查结束时，已审边数必须等于该范围的声明边数；否则明确未覆盖范围。
3. 对每条 `influence` 先把规则句改写成可比较的状态变化：**源端增加或发生一次后，目标端的哪个量增加、减少，还是仅改变可执行性**。再核对箭头方向和 sign；“从牌库抽一张”会减少牌库内容，不能因文字含有“从牌库”而误标为正向。条件成立、事件发生与状态存量必须分开判断。
4. 每条带限定词的边先做**子集反例 / 对称覆盖测试**：还原去限定词后的核心规则，并枚举相关互补集合（例如友方 / 敌方、玩家 / AI、控制角色 / 普通角色）。只要范围外存在满足相同前提且产生同一结果的实例，该规则就不是子集规则：改成通用边，把决策方式、数值或时机差异写入规则文字；不得补一条镜像限定边。只有范围外被玩法条件明确排除，或会产生不同结果，才保留限定词。决策者不同本身不构成子集规则。
5. 通过子集测试后，再对**组合限定词逐项删除**：分别移除每个谓词，核对规则的真实适用范围是否改变。某条件被其他限定词蕴含、没有参与实际判定，或只为展示属性而存在时必须删除；逐规则记录至少一个范围外反例或明确的排除证据。控制身份与阵营可以是不同维度，但只有实际参与该边判定的维度才能保留。
6. 一个限定投影连接多条边时，限定词会分别收窄每一条边；不得按画面、颜色、共享端点或投影分组后只给一个结论。
7. 规则适用于概念的全部实例时必须不加限定词。限定词只缩小单端适用范围，不改变概念身份、不表示范围外被禁止，也不能替代“同一实例/同一持有者”的关联。
8. 逐项回查原玩法问题与证据表，避免只审图中显眼的边而遗漏共享投影后的其他规则。

### 6. 形成并执行已授权差异

1. 审查模式止于逐规则建议，绝不写入。写入模式先列出 mutation 清单：对象、修改前后字段、证据、依赖顺序与预期版本。
2. 严格按阶段 1.5 已批准的容器计划创建文件夹和空白机制图：`mechanic-folder create --name <单段名称> [--parent <已有相对目录>] --workspace-revision <scopes.revision>`，再用 `mechanic create --id --name --scope [--folder <已有相对目录>] --workspace-revision <scopes.revision>` 创建图。目录不会隐式创建；不能传文件路径、原始 document、节点、规则、布局或视图字段。每次容器写入后回读 `scopes` 取得下一次顶层 `revision`。容器完成前不得写入概念或规则。
3. 概念写入使用 `resourceRevisions.definitions`；规则写入使用 `resourceRevisions.mechanics[mechanicId]`。每个命令必须携带目标 `--revision`；普通在线写入还必须携带当前 `--project-generation`、当前 `--session` 与 `--connect`。成功后使用返回的新 `resourceRevision` 串联同资源的下一步。创建目标机制后，先 `session open`，再写入概念、规则或该图元数据。
3. 规则新增使用 `--mechanic --source --target --relation`；`influence` 再提供 `--sign`。`--text` 写入规则文字，`--text ""` 清空文字但不改变结构推理。要移除限定词时传相应的空 JSON 数组；受约束写入器会同步清理失效投影坐标。
4. 机制拆分或迁移后，用一次 `mechanic update --mechanic <id> [--name <名称>] [--scope <范围>] [--remove-isolated-concepts <JSON字符串数组>] --revision <resourceRevision>` 原子收窄旧图职责并移除迁移残留成员。每个待移除概念必须不再被该图规则端点或限定词引用，且仍被其他机制图引用；操作只删除目标图成员和本图坐标，绝不删除全局概念、其他机制成员或视图。任一成员不满足条件时整次更新显式失败、零写入。
5. 当前图编辑结束必须发出一次 `session close`，不等待它的 `jobId`；不得额外手动调用 `mechanic arrange` 造成重复排版。遇到 `CONCEPT_AGENT_LOCKED`、`AGENT_EDIT_SESSION_REQUIRED`、`AGENT_EDIT_SCOPE_MISMATCH`、引用阻止、版本冲突、工作区锁或发布失败，立即停止受影响链路并只读重查；不得改用其他写入口。若 `AGENT_EXPORT_FAILED` 且 `canonicalCommitted:true`，canonical 已提交：记录真实 revision、暂停后续依赖操作，不能自动重试或声称回滚。

### 7. 回读并重新覆盖检查

1. 对已关闭且需要确认的图，先查 `session status`；随后只用 `game-mechanic-search` 允许的 `scopes/search/graph/node/impact` 回读，核对实际字段、边数和 mutation 清单；必要时重查相邻规则与限定边。
2. 报告实际声明的变化、工具推导结果、已验证运行时事实与仍未知项；图查询成功不等于运行时通过。
3. 复核写入后范围内的“已审规则卡数 / 总规则卡数”、“已映射概念数 / 总概念数”、“已映射边数 / 总声明边数”、限定边数、`is-a` 数、单链候选数与未决项。每个保留的设计锚点必须仍能指向作者确认的预期机制；任何不一致都不是完成。
4. 按机制容器计划做层级回读：每张图都能回答其读者问题，规则卡归属唯一，跨图依赖已写入 scope/报告，且没有因“完整建模”而形成无法独立阅读的总图。发现图的边界失效时，先调整图归属或容器，再复做受影响规则的覆盖检查。

## 快速决策边界

- `概念〔属性〕`：属性独立筛选该端点实例，且规则只适用该真子集时可用限定词。
- 先问“规则是否只适用于子集”，再问“端点属性是否真实存在”。后一个问题不能替代前一个；阵营、控制权或决策者不同，但前提与结果相同，仍是一条通用规则。
- “自己的区域”“同一目标”“全部对象均满足”“在事件之后”：不是限定词；写入规则文字，或在未来由专用关系能力表达。
- 反复出现的条件不是新概念；只有它拥有独立规则与复用价值时才升级为概念。
- 单链中间量不是概念：先查完整范围中的额外关系，再查作者确认的设计预留；两者皆无时，将规则压缩为直接连线，把结算细节留在规则文字。
- 设计预留不是当前事实：它可以保留概念锚点，但不得作为现有规则、运行时行为或新增连线的证据。
- 缺边、未找到路径或未引用概念只表示当前模型没有证据，不证明玩法不存在。
