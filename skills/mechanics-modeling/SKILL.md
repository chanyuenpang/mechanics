# Mechanics 建模

只运行 `node <项目>/.mechanics/tools/workspace-tool.mjs`。工具直接读写项目 JSON，不依赖 CLI、网页或 HTTP；DSH 检索/图卡插件不提供写入能力。使用与本 skill 配套的工具合同（`contractVersion >= 7`，打开草稿时返回）；旧工具不具备完整保存门禁，应同步受管工具，不能用人工检查代替。

## 默认流程：打开 → 编辑 → 保存

1. **打开草稿**：目标已知时直接 `draft open --mechanic <机制ID>`，使用返回的草稿 ID 与路径，不必先跑 `guide`、`scopes` 或查询。新建时加 `--name <名称> --scope <范围>`，可加 `--folder <已有目录>`；已有可继续使用的草稿不重复打开。
2. **编辑相关内容**：只按任务和编辑工具需要，定向读取、修改返回的 `definitions.json`、`rules.json`、`mechanic.json` 中相关部分。它们包含全库定义/规则和当前图；保留无关条目，不要求三份逐一通读、全量人工比对，也不要自行编写预检脚本。字段不确定才查 `guide` 的模板。只改草稿，不直接写 canonical，不填写几何缓存。
3. **直接保存**：`draft save --draft <draftId>`。save 自行检查格式、版本、ID、全工作区引用、概念锁、基线冲突和保存结果；失败时给出诊断。**不需要先调用 `draft validate`，不需要另一次审批或成功后固定重查。** `saved: true` 即本次保存完成，按返回结果简要交付。

脚本负责可机械判定的结构、引用与写入安全；建模师负责规则含义、证据与颗粒度。不要把脚本校验职责变成 Agent 的人工核对清单。

## 仅在需要时使用

| 情况 | 操作 |
| --- | --- |
| 字段合同未知、版本变化或字段报错 | `guide`：查本次需要的模板/约束；不要求每次编辑重读 |
| 目标机制或已有目录未知 | `scopes`：定位目标；基线由 open/save 管理，不手抄 revision |
| 概念身份或规则证据不明 | 选择合适的 `search`、`node` 或 `impact`；不是全部依次调用。模糊候选仍须用稳定 ID 消歧 |
| 只想检查、不想提交 | `draft validate --draft <draftId>`：同一保存前检查的 dry-run，不发校验凭据，也不是 save 的前置条件 |
| 保存报错 | 按错误中的路径、字段、ID 定向检查和修复；修好后直接 save |
| 用户要求展示、分析或保存结果不确定 | 仅对相关目标查询/读取，不把全库复读设为常规结尾 |

- 格式/引用/锁等预检失败不写 canonical，草稿保留；冲突后重新打开最新基线，仅重新应用本次意图，不强行重放旧全库副本。
- 脚本不会替你解除其他图或视图的引用。只有报错指出跨文件依赖、且任务确需清理它们时，才处理相应消费者；超出单图草稿能力则交接，不先保存已知断引用状态。
- 写入故障区分「已回滚」「回滚不完整/结果不确定」与「已保存但清理有警告」。按实际结果处理，不能把已提交后的清理警告当作未保存而重试整次修改，也不能对回滚失败声称零写入。
- 多张图仍顺序打开、保存，再开下一张，避免全库草稿基线互相过期。无需为普通新增或文字修改制作额外分类表、比对报告或请求重复批准。

## 图与文件夹

- 文件夹回答「去哪里找」，图回答「这一张解释什么」。沿用合理分类，按**领域/内容类型 → 稳定内容族或主要机制线**分层；同层使用同一分类轴，不混放类别、具体物品和效果。不要镜像源码或按稀有度、品质、版本复制多套图；正交筛选可复用已有标签。
- 共性图解释共享资源、事件和状态转换；物品图解释具体聚合物怎样接入它们。目录不产生分类关系、继承、规则所有权或生效范围，共享概念和规则不复制。
- 分类总览只保留必要类别和范围，叶级图整理具体物品，不展平全部后代。简单同族可合小图，复杂单体或独立机制线可分图；不强制一物一文件，也不按每条边碎拆。
- 每张图的 `scope` 写清本图问题与边界。零散物品可按真实来源/类型小型收纳，注明不声明共同玩法；不为连通而造因果，未知效果允许保留孤立身份。
- `--folder` 相对 `.mechanics/mechanics`，只能使用已有目录，省略则新建到机制根。已有图不再传新建参数，不能借此搬图。只有任务确需建目录、搬图或重命名文件时才交由支持目录管理的流程处理，不绕过工具直接修改 canonical；目录还影响导航和文档分组。

## 图的颗粒度

**单张图最多包含 25 个具体规则聚合物（道具、装备、卡牌等合计），分类总览也不豁免。** 按本图焦点与所选规则端点中的具体物品身份去重；规则带入的物品也算，类别和共享资源不算。少于 25 但多主题或难以追踪时仍应拆分。先按同粒度类别/主要用途分组，确无语义差异再分册，不删除身份、合并不同物品或隐藏代价来凑数。

这是建模语义约束，不是「总节点 ≤25」。当前协议没有统一的物品类型字段，脚本不会按名称猜测具体物品数；只在创建/整理聚合物时确定这个范围，普通文字修改不重新审计全库。焦点数、所选规则数、投影节点数由 save 返回，不要求 Agent 手数或每次报告四项数量。

- 范围明确的新图优先 `ruleSelection: "explicit"`：只展示固定规则与焦点、规则端点，不继续展开邻边；加入焦点不会自动加规则。
- 省略该字段表示焦点一跳邻接规则与固定规则并集，仅在有意观察邻域时使用。共享资源可能带入更多物品；不是固定规则少就一定图小。
- **仅在拆图或切换选择模式时**，针对本次意图决定需保留的规则和上下文，不能只改模式而漏掉效果。缩小的是本图引用范围，不是全库定义/规则，不靠折叠、缩字或排版掩盖超量。复杂批量归类可用简短分组表辅助，不默认另造报告或持久化第二份真相。

## 规则聚合物：一物一概念

每个具体道具、装备、卡牌都保留独立稳定概念、名称和定义，跨图复用。**即使没有其他引用、只有一组效果，甚至效果尚未明确，也不按冗余中间节点省略。** 普通无独立职责的单链中间量可压回规则文字，但聚合物身份是明确例外。

建模师可将它理解为「获得后这组规则才激活」的隐含条件入口；**不要求另画获得、拥有、激活节点或通用激活边**。真实的获得时触发、装备、使用、打出、命中、消耗等条件和例外仍须按证据保留，不把所有物品误写成持有即无条件生效。

- 物品直接连接共享机制/资源/事件，保留收益与代价；触发、对象、限制通常写入 `ruleText`，有独立机制职责的状态/输入才建节点。不要把每个条件短语拆节点，也不要造未支持的 `condition` 字段。
- 虚构例：「守护护符」使用独立 `ward-amulet` 概念连接 `shield`，规则文字为「装备期间，每次受到伤害后获得 1 点护盾」；不补仅用于解释隐含激活的占位节点。
- 未知效果明确待确认，不按名字编造，不把建模待办写成已确定事实。缺边或未找到路径只代表模型证据不足。

## 关系与写入边界

- 真实子类才用 `specializes`（子概念 → 唯一父概念），不是包含、目录归属或「有某效果」，也不自动推出影响继承。需要方便地设置父类时可用 `isa set --draft <draftId> --concept <子概念> --parent <父概念|none>`；它改当前草稿，之后直接 save，无需逐个再 validate。批量编辑仍可按模板修改草稿，不强制逐节点调用辅助接口。
- 规则全局唯一，同一有向端点对只保留 `<source>-2-<target>` 一条；多个条件和例外合入规则文字。影响规则按模板给出方向、`sign`、`inheritance`，正负不是玩家视角的好坏。限定词只缩小该规则端点的真实适用子集，不改变概念身份。
- definitions/rules 草稿是全库副本，不能按本图范围裁剪。`explicit` 只隔离选边范围，不隔离共享规则内容的变更。脚本自动检查候选引用，不要求 Agent 提前遍历全部消费者。
- 保存只提交 JSON；保留有效位置、清除过期路径缓存，新建图按规则维护导出选择。网页排版、视图更新、文档导出均未执行，不声称这些派生操作已经完成。
