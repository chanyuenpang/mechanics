# Mechanics 建模

只运行 `node <项目>/.mechanics/tools/workspace-tool.mjs`。工具直接读写 canonical JSON，不依赖或调用 CLI、网页、HTTP 服务、自动排版或文档导出。

DSH 插件当前只提供只读能力（检索与图 widget），**没有**写入工具；在装了插件的宿主里建模写入仍然走下面的 JSON 草稿流程，不要以为插件可以代劳。

`draft save` 在**新建**机制图时会顺带维护 `workspace.json` 的 `exportSelections`，结果里回报 `exportSelection`：`added`（补了一条单独选择）、`already-selected`、`covered-by-folder`（所在直接文件夹已选中，按互斥规则不补）、`legacy-all`（工作区未启用显式清单）。已有机制返回 `existing-mechanic`。视图永不自动导出；文档仍需显式生成。新建且工作区启用了显式导出清单时，保存会检查 `workspace.json` 的语义基线，不符以 `RESOURCE_REVISION_CONFLICT` 失败并保留草稿。

## JSON 草稿流程

1. 先运行 `guide`，以脚本返回的概念、影响规则与 is-a 规则模板为唯一草稿字段合同；不要凭记忆编造 JSON 字段。
2. 用 `scopes` 读取现有机制、文件夹与 revision；用 `search/node/impact` 查稳定 ID 和已有关系。先按下文确定归类、单图问题与纳入/排除范围，再开草稿；模糊候选须以稳定 ID 再查一次，不能按同名重新造概念。
3. `draft open --mechanic <机制ID>` 是唯一编辑入口，返回 `definitions.json`、`rules.json` 与 `mechanic.json` 三个草稿路径。目标不存在时，必须额外提供 `--name <名称> --scope <范围>`，只在草稿中准备空机制；可追加 `--folder <scopes.folders 中的已有目录>`，路径相对 `.mechanics/mechanics`，省略则落机制根目录。目录不存在报 `FOLDER_NOT_FOUND`；已有机制不要再传 `--name/--scope/--folder`（会报 `DRAFT_TARGET_EXISTS`），不能借此搬图。
4. 草稿会移除坐标与路径缓存；只编辑返回的结构 JSON，绝不直接编辑 canonical，也不要自行写回几何字段。definitions/rules 是**全工作区完整副本**，不是本图子集；保留无关条目。涉及多个图时顺序开草稿、校验、保存，再重新打开下一张，避免用旧全库副本覆盖新结果。
5. 编辑后先运行 `draft validate --draft <draftId>`。它校验全库草稿的定义与规则、重复有向端点、is-a 环，以及**当前机制**的引用；失败时草稿保留、canonical 零写入。它不检查其他机制/视图的全部引用，也不检查下文的 25 个物品限制或建模语义完整性；这些须另行核对。
6. `draft save --draft <draftId>` 会再次校验草稿身份和 definitions/rules/mechanic 的 base revision，以可回滚事务提交三份草稿；新建图需要补导出选择时，同事务还会写 `workspace.json`。只有此步骤成功后才创建正式机制文件；失败读取实际错误并保留草稿，不盲目重放。保存保留仍有效的既有节点位置、清除过期路径缓存。
7. 保存成功只表示 JSON 已提交；网页校验、自动排版、视图更新和文档导出均未执行，不能声称已完成这些派生操作。

## is-a

- is-a 就是 `rules.json` 里的一条 `specializes` 规则：`source` 是子概念，`target` 是它唯一的父概念（方向是「具体概念 → 父概念」）。**每个概念至多一个 is-a 父概念**；节点标签、`is-a` 徽标与展开虚线都只是这条关系的只读投影，不能创建、替代或反推关系。
- 指定、更换、清除用 `isa set --draft <draftId> --concept <子概念> --parent <父概念|none>`：它替换该子概念唯一的 `specializes` 出边（`none` 表示清除），把旧规则从该草稿机制的 `pinnedRuleIds` 移除、把新规则固定进去，返回 `changed`、`removedRuleId`、`addedRuleId`、`rulesPath`、`mechanicPath`；相同父子关系重复调用返回 `changed: false`。概念定义本身不变，之后仍要 `draft validate` 再 `draft save`。
- 需要手写 `rules.json` 时（例如一次调整多条 is-a），字段模板见 `guide` 的 `specializesRuleTemplate`，形如 `{ "id": "<子概念>-2-<父概念>", "source": "<子概念>", "target": "<父概念>", "relation": "specializes" }`；同一份 `pinnedRuleIds` 里的旧规则引用必须一并处理，工具不会替你猜。
- 多父、自连与成环都不允许；当前脚本通常返回 `DRAFT_VALIDATION_FAILED`，领域错误细节按实际输出读取。更换/清除会删除旧的**全局**分类规则；`isa set` 只同步当前草稿机制的固定引用，若旧规则被其他机制/视图引用，须先按下文的全局影响边界处理，不能把一次 validate 成功当成跨图安全证明。
- 新建概念时若同时指定 is-a 父概念，在同一 draft 里改 `definitions.json` 与 `rules.json`，再 validate/save。缺失规则端点会被拒绝；但「承诺了父类却漏写 is-a」属于业务遗漏，工具不会自动识别。
- 空机制工作区也可用 `draft open --mechanic <新ID> --name <名称> --scope <范围>` 准备新图，在同一草稿内建立概念和分类；无需先到网页创建。

## 目录与分类：先分层，再画图

- 文件夹回答「去哪里找」，机制图回答「这一张解释什么」。沿用项目中合理的领域分类，优先按**领域/内容类型 → 稳定内容族或主要机制线**组织；同层使用同一分类轴，具体物品、类别和效果不要混成同一级清单。不要镜像源码目录，也不要同时按稀有度、品质、版本等维度复制同一套图；正交筛选可复用已有标签，标签不承担规则语义。
- 共性机制图集中解释共享资源、事件和状态转换；物品图解释具体聚合物怎样接入这些机制。概念与规则全局复用，文件夹不产生 is-a、继承、规则所有权或生效范围；同目录的物品也不必有共同因果关系。
- 分类总览只展示必要类别与导航范围，叶级图整理具体物品。不要把所有后代物品展平为巨型「总览」；纯分类父概念有检索职责时可以保留，不强迫它承担玩法效果。
- 多个简单同族物品可放一张小图；复杂单体可独立成图；多条独立机制线分别成图，单体跨图仍引用同一概念 ID。不强制一物一文件，也不按每条边拆成碎片图。
- 真正无共同机制的零散物品可按稳定来源/类型放入小型兜底图，`scope` 明确「分类收纳，不声明共享玩法」，不得为了连通而制造公共因果节点。证据不足的条目允许暂时孤立。

下面仅为可选组织示例，不是必建目录，更不是新的 JSON 字段：

```text
.mechanics/mechanics/
  核心机制/           # 共用资源、事件、状态转换
  道具/回复/          # 简单同族小图、必要的复杂单体图
  装备/防护/          # 同一颗粒度的装备或装备机制线
  卡牌/反应/          # 按主要玩法职责整理具体卡牌
```

**执行边界**：本脚本只能在已有目录内新建图，不创建文件夹、不移动/重命名/删除机制文件。若方案需要这些操作，先列出目标目录和受影响机制，交由用户或支持目录管理的工作流处理后重新 `scopes`；不能用 shell 或直接写 canonical 绕过。目录改变还会影响导航和文档导出分组，不能当作纯视觉整理。

## 图的颗粒度与大小

**每张包含规则聚合物的机制图，最多出现 25 个具体物品（道具、装备、卡牌等合计）**。这是建模规范，不是 Schema 或工具自动拒绝的上限；分类总览也不能以「总览」为由豁免。25 是上限而不是凑满目标；少于 25 但多主题、条件拥挤、难以追踪输入输出时，仍应按内容族/机制线拆分。

先按实际规则选择计算，再分别记录四个量：

1. 聚合物数：`focusNodeIds ∪ 所选规则的两端` 中，去重的**具体物品身份概念**数量，必须 ≤25。同一物品有多条效果边只算一个；规则带入的物品也算。类别、共享状态/资源不算物品，但不能把具体物品改称类别来规避上限。
2. 焦点数：`focusNodeIds` 的数量。
3. 所选规则数：按下表确定，不只看固定规则数组长度。
4. 总节点数：`focusNodeIds ∪ 所选规则的两端` 的去重数量，保留孤立焦点。它**不等于物品数，也不必等于焦点数**；限定词/is-a 展示还可能影响实际画布复杂度。

| 选择方式 | 实际纳入的规则 | 用途与风险 |
| --- | --- | --- |
| `ruleSelection: "explicit"` | 仅 `pinnedRuleIds` | 新建聚合物精读图、分类图及范围明确的主题图优先用它；所选规则端点会显示，但不会继续展开邻边 |
| 省略 `ruleSelection` | 焦点概念的一跳邻接规则 ∪ 固定规则 | 有意观察某概念的邻域时使用；共享资源/类别可能引入大量其他物品，规则库增长后须重新检查规模 |

- `explicit` 下只加入焦点不会自动加入规则；固定规则两端可以不在焦点数组里。由旧默认图切换时，先列出应保留的规则再固定，不能只改模式导致原规则悄悄消失。
- 一张图只解释一个清楚的问题；`scope` 写明本图覆盖和排除的内容，不用「全部规则」或模板套话夸大完整性。整体目录已分组，也不能放任单张图成为全库合集。
- 超过 25 个物品时，先按同粒度的稳定类别拆；同类仍超过时按主要机制/用途继续分组，确无语义差异再使用明确的连续分册。不得删身份、合并不同物品、隐藏代价或伪造父类来压数量。
- 拆图保留共享接口和必要上下文，每张图应能读懂自己的条件与效果。减少的是**本图引用范围**，不是全局事实；不复制共享定义/规则，不靠自动排版、缩小字号或折叠掩盖超量。

## 规则聚合物：一物一概念

道具、装备、卡牌等是携带一组规则的**规则聚合物**。每个具体聚合物必须有自己的稳定概念 ID、显示名和定义，跨图复用；即使只连接一组效果、没有其他引用，甚至规则尚不明确，也不得因「中间节点冗余」而省略它。

建模师可以把该概念理解为「获得它后，这组规则才被激活」的隐含条件入口；**这只是理解约定，不要求额外创建获得、拥有、激活节点或通用激活边**。不把已有真实的「获得时触发一次效果」规则机械删除；也不把「持有」误当作所有装备/消耗品都无条件生效。装备、使用、打出、命中、消耗等真实附加条件仍须按证据写清。

| 层次 | 保存什么 | 不要做什么 |
| --- | --- | --- |
| 物品身份 | 一个具体聚合物概念；定义说明它是什么、边界和必要别名 | 不用一段效果文字替代物品身份；不按稀有度/所在图重复建同一物品 |
| 输入与条件 | 有独立机制职责的输入/状态可连到物品；其他触发、对象、限制写在相应 `ruleText` | 不把每个条件短语都拆成节点，不添加未支持的 `condition` 字段 |
| 输出与代价 | 从物品连到共享机制/资源/事件；规则文字保留收益、消耗、例外及证据边界 | 不只保留好处；不把多个独立效果塞进一个含糊的「物品效果」节点 |
| 分类 | 文件夹/已有标签组织阅读；真实子类才声明 `specializes` | 不用 is-a 表达「有此效果」「包含」「属于目录」；不由分类自动推出生效或影响继承 |

虚构示例：「守护护符」保留独立概念 `ward-amulet`，直接连接共享 `shield`，在规则文字写「装备期间，每次受到伤害后获得 1 点护盾」；不补一条只为解释建模约定的「获得护符 → 激活护符」。一张「护符」图即使只有这一个护符，也保留它的身份节点。若还有独立的消耗或状态转换职责，再据实建边/节点，而不是为整齐而省略。

批量整理先列「物品 ID / 所属类别 / 主要机制 / 目标图 / 已知规则与待确认项」核对颗粒度和归属；这只是本次检查清单，不另存第二份概念或规则真相。未知效果明确标为待确认，保留身份；不能按名称猜规则，不能把建模待办混入已确定的定义。

## 通用建模准则与全局影响

- 规则优先：先写出触发、参与者、状态变化、条件/例外和证据，再决定概念与连线。普通单链中间量若没有独立输入、输出、状态、事件或判定职责，可把细节压回规则文字；**上节规则聚合物身份是明确例外，必须保留**。
- 限定词只缩小单条影响规则端点的真实适用子集，不改变概念身份；完整概念适用时不用限定词。字段严格按 `guide`，不自行给概念加旧协议字段。
- 同一有向端点对全工作区只保留一条规则，ID 为 `<source>-2-<target>`；多个条件、例外和结算细节合并到该规则文字。影响规则按 `guide` 显式提供 `sign` 与 `inheritance`，正负不是玩家视角的好坏；不把互斥条件下的多种效果强行概括成错误方向。
- 规则只存于全局 `rules.json`；图只选择引用。`explicit` 隔离的是选边范围，不是规则内容：修改一条共享规则会影响所有使用它的图。
- 缩图/拆图只改相应 `focusNodeIds`、`pinnedRuleIds`、`ruleSelection`，**不得按本图范围裁剪 definitions/rules 全库草稿**。删除概念/规则、改 ID、is-a 换父或清除前，先检查全部机制和视图的引用（`scopes` 不是视图消费者清单）。需要跨文件清理时，单图草稿工具不能替你原子处理全部消费者；暂停该删除/替换，报告受影响项并交接，不直接改 canonical，不先保存一个已知断引用的中间态。
- 缺边、孤立焦点、全库规则未被某图选中都不自动表示坏设计；不得据此虚构、删除或宣称运行时事实。

## 保存前后核对

- [ ] 目录与本图 `scope` 一致；类别、具体物品、共享机制的颗粒度清楚，没有用总览堆满实例。
- [ ] 每个聚合物身份仍在；本图聚合物数 ≤25，同时报告焦点数、所选规则数、总节点数。
- [ ] 收益、代价、触发和例外未因拆图丢失；未知项未编造；无多余的通用获得/激活节点。
- [ ] 选择模式有意设置，`explicit` 所需规则已固定；切换/拆图前后按规则 ID 核对覆盖，不以「验证通过」冒充语义完整。
- [ ] 未误删全库事实、复制身份/共享规则或破坏其他图/视图引用；`draft validate` 与 `draft save` 均成功。
- [ ] 保存后重新查询关键物品与规则，报告修改的图/ID、数量、未完成项；明确网页布局、视图更新与文档导出未执行。

脚本只提供受限的机制容器创建、查询、草稿校验和 JSON 草稿编辑；不提供目录管理、迁移、修复、网页视图或文档发布，不能通过本 skill 绕过这些边界。
