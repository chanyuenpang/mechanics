# 编辑通道设计：agent 展示型 widget + 受约束的 Mechanics 写入

> 前提（用户定调）：**widget 是 agent 给用户展示的界面，不是控件**——它不需要用户操作。
> 本文只写被证据支持的部分，并把 DSH 的平台限制单列。

## 一、实测能力（证据）

| 事实 | 证据 |
|---|---|
| 插件两半活在实际宿主里 | `/plugins/@veewo/dsh-mechanics/client.js` 返回 200 且字节与本地文件一致；首页启动清单含该 bundle；重启后两个工具进入会话工具清单 |
| 只读工具可用 | 会话内实调 `mechanics_search`（模糊候选）、`mechanics_search {from,to}`（成对规则）、`mechanics_graph`（3 概念 / 集合内 3 条关系） |

| 卡片有移动端/窄栏下的可读文案 | 无载荷态改为标题一行、说明一行 |

## 二、"只有普通模式才能看图卡"——这个前提不成立，要修掉

先摆事实（我实测到的现状）：

1. 本会话 preset 是 `code`（会话头 `agentPreset=code`），工具调用落在 run_code 子派发上；
2. 会话日志里 `mechanics_graph` 的承载是 `tool/code-dispatch`，只有 `name/arguments/isError/content`，**没有 meta**；
3. DSH 客户端投影 `childResult()`（`dsh-client-ui-conversation/lib/client.js:8795`）对子调用写死 `callView: null`、`resultView: null`，且不带 `meta`；
4. 契约上 `presentationMeta` 「只对顶层调用计算」（`dsh-tools` 类型注释）。

**但这只是"通道选错了"，不是"Code Mode 不配拥有 widget"。** `presentationMeta` 是随一次次顶层工具结果走的一次性投影；Code Mode 下工具全是子派发，于是它必然拿不到。插件完全可以自持一条数据通道，让卡片不再依赖呈现模式：

- **宿主侧**：`ctx.webServer.register({ kind: 'prefix', path: '/mechanics', handler })`（`dsh-host-webserver` 的公开 API；该服务器默认只绑 `127.0.0.1`），由插件自己提供
  `GET /mechanics/graph?project=<会话 cwd>&ids=<conceptIds>`，返回与工具同一份投影（形状仍由 `workspace-tool.mjs` 独有）。
- **客户端侧**：卡片在 `meta` 存在时直接用 meta（重放一致）；`meta` 缺失时（Code Mode）用 owner props 里的 `cwd` 与 `argsRaw` 中的 `conceptIds` fetch 这条路由渲染，并在卡上标明数据来源。

于是呈现模式只决定"是否顺带拿到一次性载荷"，不再决定"卡能不能显示"。草稿卡同样受益（可实时读草稿状态）。

这条通道的边界必须写死，否则就是把一个只读能力换成任意读：

- 路由**只读、只服务 `.mechanics` 工作区**：请求的 project 必须含 `.mechanics/workspace.json`，路径只用于定位该项目，不提供任意文件读取；参数非法/项目不存在一律显式 4xx/5xx。
- 路由**没有身份**：它按 URL 里的 project 读取。这与 mechanics 网页编辑器同一安全姿态（本机可信开发环境），在安装文档的"已知边界"里写明。
- 卡片**标注来源**：`来自调用结果`（meta，重放一致）与 `实时读取`（fetch）分开显示；fetch 失败显示显式错误，绝不画出看起来正常却是空的图。

上游两条仍然值得记录（非阻塞）：① `presentationMeta`/render intent 是否应覆盖 Code Mode 子调用；② 是否为打包的客户端半提供包私有 RPC。有了自持路由，这两条都不再是前置条件。

## 三、编辑通道：模型驱动，卡只展示

- **host 半**新增 `mechanics_draft`，三个动作全部走项目内 `workspace-tool.mjs` 的草稿流程（不引入第二套协议）：
  - `open`：`{ mechanicId, name?, scope?, folder? }` → 返回 `draftId` 与三份草稿摘要；
  - `patch`：`{ draftId, concepts?, rules?, mechanic? }` → 写入草稿；
  - `validate` / `save`：`save` 只在通过校验后提交，返回新 revision；失败保留草稿、canonical 零写入。
- **卡**：草稿卡展示①目标机制 ②字段级 diff ③校验状态与失败原因 ④提交状态与新 revision。纯展示，无按钮。
- **人机分工**：agent 负责 open→patch→validate→save 全程；人看图卡确认"将写入什么、校验过没过"。人不需要点任何东西。
- **收益**：agent 不再自己维护三份草稿文件路径与 revision；人在对话流里就看到写入内容，而不是从 shell 输出里读 JSON。

## 四、执行任务清单

1. **host 半 `mechanics_draft`**：三个动作 + draftId 句柄；错误码原样透出（`DRAFT_VALIDATION_FAILED` / `REVISION_CONFLICT` / `SAVE_*`）。验收：示例夹具上跑通 open→patch→validate→save，canonical 只在 save 时改变；校验失败与冲突各有一条反例。
2. **草稿卡**：四段式展示；沿用已实现的诚实无载荷文案。验收：五种状态在 `scripts/preview.mjs` 可见，模型层有测试锁住。
3. **skill 双入口说明**：`mechanics-search` / `mechanics-modeling` 写明「DSH 有插件时优先用工具，否则走脚本」，并明确"卡只展示、写入由 agent 完成、save 前必须 validate"。验收：仓库源与项目内副本一致。
4. **回归与只读演练**：聚焦测试 + `npm run check`；在 tiny-world 上做一次只读演练（open→patch→validate，不 save），确认 canonical 未被写入。
5. **上游备忘（非阻塞）**：① `presentationMeta`/render intent 是否应覆盖 Code Mode 子调用；② 是否为打包客户端半提供包私有 RPC。

## 五、非目标

- 不做卡内交互（用户定调：展示优先）。
- 不绕过草稿契约改 canonical；不做自动排版、视图结构与文档导出。
- 不为 Code Mode 的载荷缺口另造一条通道。
