# Mechanics 文件协议：工作区 v13、机制 v8、定义 v7、规则库 v1、视图 v5

> 已迁移提示：唯一 canonical 根目录为 `.mechanics`。本文件未逐段迁移的 v8/v4 与 `.game-graph` 表述仅保留作旧协议迁移背景，当前机器合同以 [`schemas/protocol.schema.json`](../schemas/protocol.schema.json) 为准。

## 当前机制图的规则选择

机制 v8 可选 `ruleSelection: "explicit"`：`focusNodeIds` 保留该图明确引用的概念，`pinnedRuleIds` 是该图唯一的规则选择；固定规则的另一端概念仍会显示，但不继续展开邻接。省略该字段时沿用焦点概念的一跳邻接规则与固定规则并集。其他值直接报错，不能在兼容解码时忽略。

多机制叠加分别遵守各自的选择，再按规则 ID 合并；显式图的焦点不会扩大其他机制的选择。视图自身的直接焦点仍展开一跳。两种选择均引用同一全局规则库，不复制规则。模式变化会改变机制资源和文档语义 revision；布局不改变语义 revision。

项目 JSON 工具 `guide` 声明此可选字段（当前 contractVersion 6）；草稿仍须 validate 后 save，保存只保留选择结果中的既有位置，不自动布局、不生成文档。自动排版按实际投影节点判断是否为空。

新建机制图默认进入**单独导出**：写入 canonical 时（网页创建、Agent 的 `mechanic create`、项目内工具的 `draft save`）若工作区处于显式导出清单模式，就为该机制图补一条 `{ "kind": "mechanic", "mechanicId": … }`；所在**直接**文件夹已被选中时不补（文件夹与其直接机制图互斥），视图永不自动进入清单。文档本身仍需显式生成；`workspace.json` 基线不符时保存以 `RESOURCE_REVISION_CONFLICT` 失败，不写半成品。

UTF-8 JSON 已由用户确认。结构的唯一机器合同是 [`schemas/protocol.schema.json`](../schemas/protocol.schema.json)。正式合同只接受工作区 v13、定义 v7、规则库 v1、机制 v8、视图 v5；缺失的必填字段绝不用运行时缺省合成。打开项目时，所有仍有迁移路径的旧协议（v7–v12）会按预览→执行自动逐级升级到 v13，任何一跳失败都不写入文件并明确报错；更早或未知的核心拓扑仍可按只读兼容模式打开（结构编辑被拒绝）。显式 `migrate` 逐级升级（v7→v8→v9→v10→v12→v13）始终可用。

## 四类文档

| 文档 | 必填内容 | 唯一归属 |
| --- | --- | --- |
| `.mechanics/workspace.json` | `schemaVersion: 13`、`kind: "workspace"`、`id`、`name`、`definitions`、`rules`、`agentExportPath`、`compositions` | 项目工作区身份、定义与全局规则入口、历史组合、最近打开与 Agent 文档路径 |
| `definitions.json` | `schemaVersion: 7`、`kind: "definitions"`、`workspaceId`、`tagDefinitions`、`nodes`、`positions` | 统一概念、Agent 锁、标签资产与默认布局 |
| `rules.json` | `schemaVersion: 1`、`kind: "rules"`、`workspaceId`、`rules`、可选 `retentionBindings` | 全工作区唯一规则库；机制图与视图只引用规则 ID |
| `mechanics/*.mechanic.json` | `schemaVersion: 8`、`kind: "mechanic"`、`workspaceId`、`id`、`name`、`scope`、`focusNodeIds`、`pinnedRuleIds`、`positions`、`taxonomyPresentation` | 某张机制图的引用范围、规则选择、局部布局与 is-a 展示状态 |
| 任意普通目录的 `*.view.json` | `schemaVersion: 5`、`kind: "view"`、`workspaceId`、`id`、`name`、`mechanicRegistrations`、`focusNodeIds`、`pinnedRuleIds`、`collapsedNodeIds`、`positions`、`structuralPresentation`、`taxonomyPresentation` | 子机制注册、显隐、组合布局、结构呈现与 is-a 展示状态，不拥有规则 |

canonical 路径相对于项目固定 `.mechanics`；`agentExportPath` 是项目内相对目录，不能与 `.mechanics`、`.git` 或 `node_modules` 重叠。递归发现普通 `*.mechanic.json` 和 `*.view.json`，可在同一目录混放；排除隐藏条目和 node_modules，不持久化第二份清单。两类 ID 分别唯一，允许机制图与视图同 ID，路径映射按 `(kind,id)` 查找。支持中文路径，拒绝路径穿越、绝对路径、非法文件名、符号链接/junction 和嵌套工作区。未知版本、未知字段、坏文件、重复 ID、非法符号都整体拒绝。

## 统一节点定义图

```json
{
  "id": "player-health",
  "label": "我方血量",
  "description": "当前分析主体的剩余血量，不指敌人血量。",
  "agentLocked": false,
  "tags": ["资源"]
}
```

`id` 在工作区内唯一，使用小写英文语义 kebab-case，长度不超过 96，拒绝 UUID 与随机十六进制片段。显示名可改；ID 不随名称改变。可选 `aliases` 保存自然语言旧称、同义词和跨语言叫法；按 NFKC、大小写与空格归一化后同概念内不得重复，且任何别名都不能遮蔽 canonical 概念 ID。不同概念可以共享同一歧义别名，搜索必须返回全部候选。

`description` 是概念本身的定义，不编码变化方向或规则。节点只有互斥的两种形态：基础节点不含 `baseConceptId` 与 `qualifiers`；限定节点必须同时提供二者，且 `baseConceptId` 必须指向基础节点。限定节点的 `qualifiers` 至少一项，key 不能重复；值只能是 `{ kind: "concept", conceptId }`（引用已定义概念）或 `{ kind: "literal", value }`（JSON 标量），不能保存运行时实例或对象。`tags` 只供搜索和人工分类，不参与概念身份、结构推理、继承或运行时判断。`agentLocked` 必填：`true` 表示该概念由用户冻结，Agent mutation 不得修改或删除；网页仍可由用户显式切换，锁不阻止规则引用。`positions` 是 `{ "节点ID": { "x": 40, "y": 80 } }`。机制图只保存自身节点位置；视图的 `positions` 是独立布局记忆，可保留当前隐藏但仍存在于统一定义中的节点坐标。Visible 只改变显示投影，不删除或用子机制局部坐标覆盖视图坐标；再次显示时恢复原位。首次出现且尚无视图坐标的节点会寻找不与已有布局重叠的位置。定义图不拥有关系边；总览可将机制图的边投影在这些节点之间并显示来源。

## 机制图与关系

```json
{
  "id": "enemy-damage-2-player-health",
  "source": "enemy-damage",
  "target": "player-health",
  "relation": "influence",
  "sign": -1,
  "inheritance": { "mode": "none" },
  "ruleText": "伤害已经命中且未被吸收时，降低我方血量。"
}
```

节点必须先定义，再在机制图 `nodeIds` 中引用；边端点必须属于该图的 `nodeIds`。规则 ID 固定使用 `<source-concept-id>-2-<target-concept-id>`。同一有向端点对在整个工作区只允许一条规则；关系、符号或规则文字变化都编辑现有规则，不另建第二条边。完整来源键是 `(graphId, edgeId)`。

`source`、`target`、`relation` 与 `sign` 共同表达结构；可选 `ruleText` 保存规则文字（最多 8000 字符）。条件约束直接写入规则文字；独立 `condition` 字段已删除，提交此字段会被拒绝。规则文字缺失、空串或纯空白时，连线、箭头和符号显示灰色；不改变结构推理。规则文字不自动求值，未填写也不证明无条件。

`sign: 1` 表示正向影响，`sign: -1` 表示负向影响，`sign: "random"` 表示随机影响。正负描述目标相对自身方向短语的变化，不表示玩家视角的好坏。消耗应表达为行动对资源的负向影响；资源支持行动可以是另一条正向影响，两者不是同一种输入。

## 影响与特化关系

`influence` 必须携带 `sign: 1/-1/"random"` 与 `inheritance`。`inheritance: { "mode": "none" }` 是默认且显式的边界：只返回作者声明的影响。`specializes` 表示“具体概念 → 上位概念”，不携带 `sign` 或 `inheritance`；每个概念至多一个父概念（同一 source 的第二条出边以 `SPECIALIZES_MULTIPLE_PARENTS` 失败），禁止自连接（`SPECIALIZES_SELF_LINK`）和闭环（`SPECIALIZES_CYCLE`）。

正向影响表示源沿增加方向变化时目标沿增加方向变化；负向影响表示目标沿减少方向变化；随机影响表示目标可能沿增加或减少方向变化，只说明方向不确定，不表示概率。随机影响位于一条路径的任意位置后，该路径结果保持随机；其他独立的确定路径仍分别保留。

`specializes` 本身不传播影响。Agent 查询会把它作为直接 `is-a>` 分类边返回，但不会自动替换端点、派生新的 influence 边或将分类关系计入正负影响结论。分类边不表示适用条件已经满足、数值相同或运行时成立。

`node` 查询另外给出**分类透传上下文**（结果字段 `taxonomy`）：从子概念沿 `specializes` 上溯，列出每个上位概念及其自身的声明边与 is-a 路径，`interpretation` 为 `classificationContextOnly`。它只用于发现与阅读，子概念并不因此取得这些影响，也不参与正负号结论。

`ruleRegistry` 可选 `retentionBindings`：每条绑定用 `mechanismConceptId`、`resourceConceptId`、`capConceptId` 声明一组“上限概念约束资源概念”的配对事实；同一资源或同一上限在全工作区只能绑定一次，资源与上限不能是同一概念。只有显式 `--include-inherited` 的 `impact` / `node` 查询才会由绑定生成派生边；派生边带 `derived` 与 `origin`，不落盘、不级联，并与作者声明的同端点规则不并存。未绑定的组合——包括两端各自 is-a 特化产生的交叉——永不派生。

路径只遍历影响边，使用未折叠原图；简单路径不重复访问节点，并设数量、深度、展开量上限。截断明确标记，不迭代累计效果。未选机制不参与计算。

右键框选与多选只在页面存在，不进入协议。群组移动一次提交完整 positions：机制手动保存、视图自动保存；共同位移限制在坐标边界内，不能逐个裁剪破坏队形。取消手势不写入。特化关系端点不能折叠；已有视图的折叠因特化边失效时仍走显式展开修复。

## 视图、最近打开与折叠

已有命名组合存于 `workspace.json` 的 `compositions`，包含 `id`、`name`、`graphIds`、`collapsedNodeIds`、`positions`。它只保存观察选择和布局，不复制节点或原始边。0.2.1 移除命名组合的界面入口，保留字段、原有内容和校验；不需要迁移文件。

独立视图示例（文件名、目录与 ID 相互独立）：

```json
{
  "schemaVersion": 3,
  "kind": "view",
  "workspaceId": "sample-card-game",
  "id": "melee-response",
  "name": "近战反制",
  "mechanicRegistrations": [
    { "mechanicId": "basic-rules", "visible": true },
    { "mechanicId": "encounter", "visible": true },
    { "mechanicId": "hand", "visible": false }
  ],
  "collapsedNodeIds": [],
  "positions": {},
  "structuralPresentation": "line"
}
```

`mechanicRegistrations` 是有序注册表，每项必须显式提供 `mechanicId` 和布尔 `visible`；同一机制不能重复注册，也不能注册视图。隐藏项仍属于视图，但不参与网页画布或 Agent 的当前关系、路径和影响范围。折叠 ID 必须属于某个已注册机制的节点；暂时隐藏导致折叠不可用时保留记忆，再次显示后重新判定。位置 ID 可以属于统一定义中的暂时隐藏节点。未打开的视图也参与全工作区校验，缺失来源不能部分加载。

可选 `workspace.lastView` 有两种互斥形式：内联状态与 `{ "viewId": "melee-response" }`，命名引用不能附带第二份勾选快照。0.4.0 打开机制只记录 `{ "graphIds": ["hand"], "activeLayerId": "hand", "collapsedNodeIds": [], "positions": {} }`；旧多图或带展示状态的内联记录只读预览，须明确保存为视图或放弃，不在启动时改写。无记录首次打开第一张机制。打开视图总是读取最新源图，重复点击也重新读取；候选验证成功后才替换画面。顶部概念表/机制图切换保留上下文，不写最近记录。

机制只看和编辑自身；命名视图在自身条目下展示已注册的子机制。视图旁的添加按钮注册子机制并默认 Visible，Visible 按钮只切换显示。注册表、组合位置和折叠自动写回 `.view.json`，源规则只读。「新建视图」从空注册表开始，也可从当前机制创建或将视图另存为。点机制离开视图不改原视图；返回视图重新读取源规则。创建文件与写最近记录是两次独立提交，后一步失败明确报告已创建路径，不重复创建或删除文件。

- 按稳定 ID 接合节点；同名异 ID 不自动合并。
- 同一图重复选择只算一次；图顺序不决定覆盖权。
- 不同图的同向或异向边都保留，来源可展开；不把异号边算成零。
- `visible: true` 的注册项组成当前模型范围，不等于当前回合已经激活的行动集合。
- 折叠在完整选图结果上执行。单入单出且不在有向环中的节点才允许折叠；摘要保留全部原始边与中间节点，重建未折叠投影即可展开。无效折叠请求报错。
- 机制位置优先于共享默认布局；视图使用自己的 `positions`，并保留隐藏节点的布局记忆。没有位置时用共享默认布局或按定义稳定 ID 寻找非重叠初始位置，不使用源机制局部布局抢占。从机制创建视图时明确复制该机制已保存的位置作为初始展示。
- 保存的折叠 ID 检查引用存在；拓扑资格在投影时再验证。成员变化保留节点位置记忆，只清理失效折叠，可整步撤销；外部改动引起的无效折叠须明确确认展开修复后才写视图，不自动丢弃。

路径输出包含原始方向、符号、规则文字、来源与 `truncated`。它查询有限简单路径，不用于闭环动态求解；截断或没有结果均不能推出实际游戏中无关联。

## is-a 展示状态（taxonomyPresentation）

`specializes` 是具体概念 → 上位概念的单向规范关系，每个概念至多一个父概念：同一 source 的第二条出边以 `SPECIALIZES_MULTIPLE_PARENTS` 失败，自连与成环仍分别以 `SPECIALIZES_SELF_LINK`、`SPECIALIZES_CYCLE` 失败。label 只是这条关系的只读展示投影，不能创建、替代或反推关系。

is-a 关系本身只由 `rules.json` 里该子概念唯一的 `specializes` 出边承担；它只能从概念的「上位概念」字段写入——网页在节点属性面板与新建/修改概念对话框里维护，Agent 用 `mech agent rule set-parent --mechanic <投影机制ID> --concept <子概念> --parent <上位概念|none>`（一次提交替换出边并同步清理各机制/视图的固定引用）。画布连线只创建影响规则，不再创建 is-a。

机制图与视图都必须显式保存 `taxonomyPresentation`：`{ "mode": "label", "expandedNodeIds": [] }`。`mode` 目前只接受 `label`；`expandedNodeIds` 是去重概念 ID 集合，表示这些子概念已在详情中展开，画布据此显示到直接父概念的虚线，并把仅为 is-a 出现的孤立父概念纳入投影。新建、迁移与保存路径都写显式值，读取时不接受缺字段，也不在运行时合成默认值。单图状态归 mechanism，叠加状态归 view；切换只改对应文件。

## 显式逐级迁移

常规读取、保存、网页和 Agent API 只接受 workspace v13、definitions v7、rules v1、mechanic v8、view v5；版本不符或字段缺失时严格失败，读取路径绝不补默认值。打开项目只会为仍有迁移路径的旧协议（v7–v12）改写文件：逐级先预览后执行，每一跳原子提交并回读，任何一跳失败零部分写入；更早或未知的旧资料仍以只读兼容模式打开、不在打开时改写。停服后使用 `mech migrate --from <旧版本> --to <新版本> --project <项目目录>` 逐级升级：`7→8`、`8→9`、`9→10`、`10→12`、`11→12`、`12→13`；默认仅预览，执行时必须带预览返回的 `--revision --execute`。`mech migrate-project --project <项目目录> --execute` 会把旧 `.game-graph` 根、旧 skill/导出与协议版本一次链式升级到当前版本。

迁移将关系输入 `belongsTo` 改为 `specializes`，为每条影响边补 `inheritance: { "mode": "none" }`，并给视图补 `structuralPresentation: "line"`；历史 `condition` 会合入 `ruleText` 后删除；不会生成或落盘派生规则。版本不匹配、候选无效、revision 冲突或回读失败均不留下部分升级。

## 当前 I/O 与保存合同

工具偏好不属于游戏文件协议：`GET/POST /api/preferences` 读写固定用户配置目录下的 `game-graph/preferences.json`，只接受 `{version:1,snapToGrid:boolean}`。它不接受任意路径，不改变工作区 revision；原子替换并回读，坏文件或链接路径明确拒绝。不同服务共享本机偏好，单布尔值采用最后确认写入；页面重新获得焦点时同步，不以浏览器缓存保存。

CLI 提供 `init/web/validate/catalog/root`、只读 `agent guide/scopes/search/graph/node/impact` 与受约束 `agent concept/rule` mutation、帮助和版本。`catalog` 在取得工作区锁后从 canonical 资料完整重建 Markdown-only catalog v5 并回读验真：一个全局 `concepts.md` 和按 `mechanics/` 实际目录聚合的 `folders/<目录>/index.md`，不会生成逐概念文件。

| 接口 | 请求与结果 |
| --- | --- |
| `GET /api/project` | 返回空项目或当前 `projectRoot`、固定 `workspaceRoot`、`agentExportRoot` 与 `projectGeneration` |
| `POST /api/project/open` | `{projectRoot,name?,id?}`；打开项目，缺少 `.mechanics` 时原子初始化；候选成功并取得锁后才切换。v7–v12 会在创建 store 前自动逐级预览并执行迁移，任何一跳失败都不写入文件 |
| `POST /api/project/export-path` | `{projectGeneration,revision,agentExportPath}`；先完整发布新读模型，再提交配置并安全清理旧生成目录 |
| `GET /api/workspace` | 返回完整已校验工作区、三层根路径、`projectGeneration`、`files: [{kind,id?,path}]`、`directories`、整体 `revision` 与每资源 `resourceRevisions` |
| `GET /api/agent` | command=scopes/search/graph/node/impact；带整体/资源版本、来源和完整性的只读语义输出，读取与保存共享队列 |
| `POST /api/agent/mutation` | `{projectGeneration,revision,resource,action,...fields}`；revision 是 definitions 或目标 mechanic 的资源版本，只允许概念与规则白名单 mutation |
| `POST /api/save` | `{ revision, kind, id?, document }`；mechanic/view 按 `(kind,id)` 查当前文件；workspace 仅允许改名称、compositions 和 lastView |
| `POST /api/mechanics` | `{ revision, document, file? }`；默认 `mechanics/<id>.mechanic.json`，可显式指定根内相对文件路径；完整创建后直接被发现 |
| `POST /api/views` | `{ revision, document, file }`；必须显式提供根内相对 `.view.json` 路径，不额外登记清单 |

写请求携带 `projectGeneration`，旧页面在项目切换后返回 `PROJECT_CHANGED`，不能把草稿写入新项目。服务支持 CORS/OPTIONS，没有 session、Bearer 或 Origin 授权；仍只绑定 `127.0.0.1` 并校验 Host、JSON、路径、版本和工作区锁。不支持操作返回 405，版本冲突/同名冲突返回 409，请求超过 3 MiB 返回 413，合同无效返回 422，提交结果待确认或新建部分完成返回 500。文件内容仍受 2 MiB 限制。

整体 `revision` 与每资源 `resourceRevisions` 都只覆盖**语义内容**：对配置、定义、全部机制图和视图文件按路径排序，剔除展示字段（`positions`、`projectionPositions`、`routeCache`、`nodeColors`、`nodeStyles`，以及配置中的 `lastView`）后取 SHA-256，并包含普通目录集合。因此格式变化、坐标移动、配色改动、连线路径补算和“最近打开”记录都不改变版本戳，而结构、命名、引用、规则正文、成员与显隐等语义变化一定改变它。`resourceRevisions` 按 `workspace`、`definitions`、`rules`、`mechanics[id]`、`views[id]` 分别给出，供写入与 Agent 会话做 compare-and-swap。

页面自动保存视图同样经过 revision 校验。视图自动保存与规则保存共享串行队列，每次捕获明确目标与快照；失败暂停后续自动写入，保留草稿供导出，显式重新读取确认后才恢复，不自动采用新版本重试。

保存带读取时的整体 revision 与每资源 `resourceRevisions`，在单工作区队列内重新读取和验证引用后写入。**冲突判定与提交粒度一致**：一次写入只落一个（或几个）资源，只有这些资源的语义版本变化才构成冲突，其他页面写别的文件或补算布局不再拒绝一次本身安全的写入；缺少每资源基线时退回整体比较，绝不放宽为无条件写入。冲突信息必须点名被改变的文件。结构操作（新建、移动、删除文件与目录）仍要求整体版本未变。未知版本、断引用、过期版本或写入失败均不能当成功。已有文件用同目录临时文件替换，新建通过硬链接发布完整临时文件并原子拒绝同名目标，不再同时写清单。不支持该文件系统操作时明确失败。创建父目录后失败可能留下空目录；提交后回读失败需确认磁盘状态。详见[架构设计](架构设计.md)和[编辑器使用说明](编辑器使用说明.md)。

禁止把假设模型自动标记为实际规则。机制覆盖、结构比较与 agent 查询合同仍在讨论，见[模型优化讨论](模型对agent的价值与优化讨论.md)。实时战斗状态和行动规划不属于当前模型。
