# Mechanics 更新与升级

本页说明`@veewo/mechanics` 的三个更新层次，以及更新后各自需要做什么。三层互相独立：只升 CLI 不会自动改项目，只同步项目也不会改宿主配置。

| 层次 | 是什么 | 更新入口 |
|---|---|---|
| CLI | 全局命令 `mech` | `npm install -g @veewo/mechanics@<版本>` |
| 项目内受管资产 | `.agents/skills/{mechanics-search,mechanics-modeling,mechanics-doc}`、`.mechanics/tools/workspace-tool.mjs` | 网页打开项目后后台同步，或在项目目录运行 `mech sync` |
| 宿主接入 | Codex 的 MCP server 配置 / DSH 的插件包 | 各自的配置与重启，见下文 |

## 版本号提升规范

@veewo/mechanics 使用“主版本.次版本.修订版本”。以 npm 已发布最新版本为基线，同一批改动取所需最高等级，只提升一档，不因提交数叠加。发布前核对包清单、锁文件、Git tag 与 npm registry。以后发布者按此规范自动选版本号，不为常规升版重复询问；发布范围、不可逆迁移或重大兼容取舍不明时才先确认。

- **修订版本（patch）**：不改变文件协议、对外查询或工具合同及既有承诺行为的修复；仅改文档、受管 skill 文案或样式。例如 0.8.3 → 0.8.4。
- **次版本（minor）**：新增可选功能，升级对外查询或工具合同；或持久化 Schema 升版且有已验证的旧版迁移路径。即使旧项目能自动迁移，严格读写合同仍已变化，发布说明须列明迁移与回滚影响。例如本次工作区 v13→v14、机制 v8→v9，选 0.8.3 → 0.9.0。
- **主版本（major）**：移除或重定义既有语义，停止支持旧接口，或持久化变化没有安全迁移路径；必须明确升级前备份、受影响调用方和回滚边界。0.x 阶段仍主动按此约定分级，但不宣称预 1.0 具有稳定兼容承诺。
- 包版本不代替工作区/机制 Schema、Agent 查询协议、项目工具合同或受管 skill 版本；各自按自身合同提升，在变更日志中写清。DSH 插件是独立包，另行决策和发布。

## 发布后的本机正式包验收

每次发布 `@veewo/mechanics` 或 `@veewo/dsh-mechanics` 后，发布工作**不止于 npm publish 成功**：先回读 registry 中的精确版本，再将本机正在使用的对应包切换为该版本的 npm 正式包，并核对实际解析源。只有发行包已安装、非源码 link、版本与依赖一致，才能声称“本地已更新”；只看到 `mech --version` 或插件 `package.json` 的新数字不足以证明安装来源。项目受管工具的 `mech sync` 属于另一步，不自动修改任何游戏工作区。

```powershell
npm view @veewo/mechanics@<已发布版本> version
npm install -g @veewo/mechanics@<已发布版本>
npm ls -g @veewo/mechanics --depth=0
mech --version
dsh plugin --profile web remove @veewo/dsh-mechanics  # profile 原来为 link/file 时先移除
dsh plugin --profile web add @veewo/dsh-mechanics@<已发布版本>
dsh plugin --profile web list
npm view @veewo/dsh-mechanics@<已发布版本> dependencies --json
```

- CLI 的全局安装与 profile 的插件安装都不得留下 `link:`、`file:`、`workspace:` 或指向工具仓库的路径。使用精确版本而非 `latest`，安装后核对 profile 依赖声明、实际包所在目录与插件对 Mechanics 的依赖；若仍为源码链接，不算完成，按安装命令修复后重新核对。
- 插件变更只有在 DSH 新进程中加载；重启承载当前对话的实例前，必须按重启流程先干运行并取得用户对**本次**重启的明确同意。未同意时可完成包替换，但要报告“已安装、待重启”，不得称运行中的 GUI 已换版。重启后另行检查工具注册与实际图卡，不以离线预检冒充页面验收。
- 本机安装/验证失败时发布可以已完成，但必须分别报告 registry 状态与本地状态，不以改源码、建链接或启动另一个服务器代替正式包安装。

## 核对当前版本

```powershell
mech --version                                   # 本机 CLI 版本
npm view @veewo/mechanics version                # registry 最新版本
node <项目>/.mechanics/tools/workspace-tool.mjs guide   # 项目内工具契约版本 contractVersion
```

项目内工具的 `contractVersion` 是**判断功能可用性的唯一依据**：

| contractVersion | 能力 |
|---|---|
| ≥ 5 | `search --query` 的模糊回退、`graph --ids` |
| ≥ 6 | 新建机制图时顺带维护导出清单（curated 模式补一条独立选择；文件夹已覆盖则不补；视图永不自动导出），且不因此绕过草稿校验 |
| ≥ 7 | 默认直接 `draft save`，统一完成草稿及全工作区引用、权限、基线检查和提交确认；`draft validate` 仅作可选预检。`draft open` 返回合同版本，无需为已知目标固定先跑 guide/scopes |

CLI 版本旧、但项目内工具已同步到新版本时，功能仍然可用；反之则不可用。

## 升级 CLI

```powershell
npm install -g @veewo/mechanics@latest
mech --version
```

升级 CLI 只替换全局命令，**不会**动任何项目的 `.mechanics` 数据，也不会自动改写项目内的 skill 与工具副本。

## 同步项目

在项目目录（或任意子目录）运行：

```powershell
mech sync
```

它把受管 skill 与 `workspace-tool.mjs` 更新为**当前已安装 CLI 自带的版本**。以下情况必须同步，否则会出现"CLI 新、项目旧"的错配：

- 项目内工具的 `contractVersion` 落后（新命令或新参数报 `TOOL_INVALID`）；
- 受管 skill 的 `mechanics_skill_version` 落后（skill 描述的能力与工具不一致）；
- 从别的机器或别的 CLI 版本初始化的项目。

网页打开、初始化或进入关联项目后，会在后台执行同一套受管资产同步，页面无需等待。同步期间仍可读取和保存项目；同一项目进行中的同步会合并。失败会显示非弹窗提示并记录服务日志，修复原因后重新打开项目可重试。后台同步尚未完成时，不应视为项目工具已经更新；需要等待明确完成时使用 `mech sync`。

同步以安装包内容替换这三个受管 skill 的完整目录，并更新工具副本；不要在受管目录内保存自定义修改。普通文件占用目录、符号链接或权限错误会明确报错，其他 skill 不受影响。网页使用当前运行服务所来自的包，不会联网升级；升级包后需要重启 Mechanics 服务。

## 协议迁移

工作区协议（workspace/definitions/rules/mechanic/view）只把当前版本当作可写合同：未识别字段、缺失的必填字段或坏引用会**严格失败**，不用运行时默认值修复。打开项目时，所有仍有迁移路径的旧协议（v7–v12）自动先预览再执行逐级迁移；更早或未知的旧资料只按核心拓扑兼容模式只读打开（结构编辑被拒绝）。也可以显式执行迁移：

```powershell
mech migrate --from <旧版本> --to <新版本> --project <项目目录>          # 默认只预览
mech migrate --from <旧版本> --to <新版本> --project <项目目录> --execute
```

旧 `.game-graph` 目录使用 `mech migrate-project --project <旧项目目录>`（同样默认预览）。迁移前先提交项目，迁移后运行 `mech validate` 核对。

## 更新宿主接入

### Codex（MCP Apps）

MCP server 由全局 `mech` 启动，因此升级 CLI 后**重启 Codex** 即可用上新版本。若修改了配置里的 `cwd`，同样必须重启。

### DSH 插件

```powershell
dsh plugin --profile <profile> add @veewo/dsh-mechanics@latest
```

然后重启宿主（插件在启动时组装）。两点注意：

- 插件运行时要用 `@veewo/mechanics` 包里的 widget 资产，因此插件版本与其依赖的 mechanics 版本要匹配（插件 package.json 已声明依赖，`dsh plugin add` 会一并安装）；
- 若 profile 里装的是**指向源码目录的 link**（开发态），升级发布版需要先 `remove` 再 `add`，否则读到的仍是本地源码。

插件升级后，项目侧仍需满足前两节：**项目内工具版本足够新**（`mech sync`），否则工具调用会带着项目工具自己的错误码失败。

## 排障

| 现象 | 原因与处理 |
|---|---|
| 新命令报 `TOOL_INVALID` / 未知命令 | 项目内工具旧：`mech sync` |
| 工作区读取报协议版本错误 | 需要 `mech migrate`（先预览），不要手工改文件 |
| DSH 里工具不存在 | profile 没装或没重启宿主 |
| DSH widget 显示红色错误页 | 逐字读页面上的错误：项目没有工作区、ID 不存在、widget 资产缺失（多为插件与 mechanics 版本不匹配） |
| Codex widget 不出现 | 工具配置、工具调用、宿主显示是三个独立结果，分别核实 |

## 回滚

- CLI：`npm install -g @veewo/mechanics@<旧版本>`，随后在项目里 `mech sync` 把受管资产退回同一版本；
- DSH 插件：`dsh plugin --profile <profile> remove @veewo/dsh-mechanics` 并重启；
- 协议迁移不可自动回退：迁移前提交项目，回滚时用 Git 恢复。
